# ADR-0021: Attendance is captured in Subsplash Check-In and imported, not captured in this app

**Status:** Accepted
**Date:** 2026-08-21

## Context

ADR-0015 built this app's own check-in capture: a web `/kiosk` surface, device-authorized iPad tokens, session/roster/drop-off/pickup logic, printed labels (`components/labels/`, `lib/labelPdf.ts`), and a partially-built native wrapper (`ios/`, uncommitted). In practice, the church runs **Subsplash Check-In** at the door for Liturgy and Sunday School — so attendance was being captured twice, once in Subsplash (the one volunteers actually use) and once here (unused).

Subsplash has no API for per-person check-in data: the vendored `openapi.yaml` has no check-in/attendance REST path, `AttendanceRes` is a schema stub with no operations, and the full webhook event list (`donation.create`, `profile.create/update/delete`, `end_user_login_event.create`, `response.create`) has nothing attendance-related. The only place per-person check-in data exists outside Subsplash's own UI is the **Check-In dashboard's own attendee export** (Events → Check-In → an occurrence → Total Attendance → Export) — an authenticated web-app surface, not a documented or versioned API.

## Decision

Retire this app's check-in capture entirely. Subsplash Check-In becomes the sole system of record for *who checked in*; this app's role narrows to reporting and follow-up (occurrence attendance, series frequency, absentees, email-parents) over attendance **imported** from Subsplash by hand, on roughly a weekly cadence.

- **`lib/subsplashExportCsv.ts`** parses a Subsplash Check-In attendee export — confirmed byte-for-byte against two real exports pulled from the live dashboard (a single-occurrence detail export and a full-year "All Check-ins" range export), which turn out to differ in header casing ("First Name" vs "First name") and date/time column shape (full datetimes vs. a bare date + bare time meant to be combined). Both are handled uniformly; an unrecognized row is dropped into a `skipped` list with a reason, never guessed at.
- **`scripts/sync-subsplash-attendance.ts`** POSTs the parsed result to `POST /api/attendance/import`, one occurrence at a time so a bad occurrence doesn't sink the rest of a run. Point it at a CSV you export yourself from the Subsplash dashboard (Events → Check-In → an occurrence → Export, or the "All Check-ins" range export for a backfill). Re-running it (the same file, or an overlapping date range) is a no-op beyond updating rows to match the export's current state — the unique `(series_id, occurrence_date, profile_id)` constraint from ADR-0015 makes re-import idempotent by construction, not just "probably fine" (a synthetic guest id is derived deterministically from the occurrence + attendee name for exactly this reason — see below). **Full automation of this step (a scheduled script driving the dashboard itself) was investigated thoroughly and abandoned — see Consequences.**
- **Imported rows land in the existing `check_ins` table**, not a parallel store — `method: "subsplash"`. Every downstream consumer (`/api/attendance/report`, `/absentees`, `/email`, `summarizeSeriesFrequency`) keeps working unmodified; only presentation changed (a "Subsplash" source badge in place of a check-in operator, since imports carry no such actor — but real check-in/check-out timestamps and the drop-off adult's name *are* in the export and preserved).
- **Name/email resolution is best-effort, and failure is visible, not silent.** `lib/attendanceImport.ts` matches an exported attendee to a directory profile by, in order: Subsplash profile id (if the source ever provides one) → a full name unique across the directory → if the name is ambiguous, narrow to the candidate whose email also matches. Email is deliberately **not** a primary, name-independent match key: confirmed against a real export, a child's "[Checked in] Email" column is frequently the *guardian's* email (Subsplash pre-fills it from the household's contact), not the child's own — matching on email alone would silently attribute a child's attendance to their parent's profile instead. An unresolved attendee is still recorded — as a guest row keyed by a deterministic id derived from the occurrence date + their normalized name (not a random id, so re-importing updates the same row instead of duplicating it) — and logged to the new `attendance_imports` table, which the report UI surfaces as a named warning: an admin can see exactly who didn't match and go fix the mismatch (typo, name change, not yet in the directory) instead of that person quietly reading as "absent" every week.
- **`app/api/attendance/import`** accepts either a bearer token (`ATTENDANCE_IMPORT_TOKEN`, timing-safe compared) or an admin's own session — so a payload can be POSTed from the script or replayed by hand while debugging.
- **Everything specific to in-app capture is deleted**, not just disabled: `/kiosk`, `/api/kiosk/*`, `/api/devices/*`, `/api/attendance/reprint`, the `devices` table, `lib/deviceAuth.ts`, `lib/labelPdf.ts`/`labelStock.ts`, `lib/matchCode.ts`, `components/labels/`, and the check-in POST/PATCH/DELETE handlers on `/api/attendance` (GET — reading who's checked in — survives, now reading imported rows). The uncommitted `ios/`/`android/` native wrappers are dropped along with it. `check_ins` columns that only ever served capture (`droppedOffBy*`, `matchCode`, `checkedOutAt/By`) are kept (nullable, harmless) rather than dropped, since dropping a column is irreversible and buys nothing here.

## Consequences

- **The export format is undocumented and unversioned.** Subsplash can change it in any release with no notice — the two export types already confirmed to differ from each other (header casing, date/time column shape) is a preview of that risk, not a one-time surprise. `lib/subsplashExportCsv.ts` fails loudly (a row lands in `skipped`) rather than guessing at an unrecognized shape.
- **Attendance is only as fresh as the last manual export** — realistically weekly, not daily. Acceptable for this app's actual use (reports reviewed periodically, absentee follow-up), not real-time.
- **Imported attendance carries no check-in operator identity** — Subsplash's export doesn't say who ran the kiosk, only who checked a person in and (often) who dropped them off. Reports that used to show "checked in at 9:04 by office@…" now show a "Subsplash" badge for an imported row's operator instead; real check-in/check-out timestamps and the drop-off adult's name *are* preserved from the export.
- Worth raising with the Subsplash CSM in parallel: whether automated dashboard access is permitted under their terms, and whether per-person check-in data is on their API roadmap. An official endpoint would make automation viable outright.

### Full automation was investigated and abandoned — record of what was tried, for anyone tempted to try again

A scheduled script drove the Subsplash dashboard via Playwright to fetch each series' export without a human clicking Export. It got as far as fully working end-to-end mechanics — real login-page structure, the dashboard's shareable per-series report URL (`https://dashboard.subsplash.com/-d/#/library/repeating-events/{seriesId}/check-in-report?minDate=...`, where `{seriesId}` is exactly the Subsplash repeating-event id `lib/events.ts`'s `listSeries()` already exposes), and the Export button's client-side ZIP generation (confirmed via its "PK" magic bytes and captured via Playwright's `download` event, since there's no distinct API call to intercept instead) — but **authentication itself could never be made to survive an unattended run**, across every approach tried:

1. **Fresh username/password login from GitHub Actions.** Silently rejected: the form filled and submitted correctly with human-confirmed valid credentials, yet bounced back to the same plain login page — no error text, no 2FA/OTP screen shown either. Consistent with Subsplash flagging the runner's IP/device as unrecognized.
2. **A captured session (Playwright `storageState()`, cookies + localStorage) replayed from CI.** Also rejected. Suggested device/IP trust was checked continuously, not just at login.
3. **The same captured session, replayed locally** — same machine and network it was captured on, to isolate IP as a variable. *Still* rejected. Inspecting the captured file directly explained why: it contained only Google Analytics and reCAPTCHA cookies, **no real Subsplash auth data at all**, despite the browser visibly showing the signed-in dashboard at capture time. `storageState()` only captures cookies and localStorage; Subsplash's actual session apparently lives elsewhere (IndexedDB is the likely home for it), which `storageState()` silently omits.
4. **A persistent Chrome profile directory instead** (`chromium.launchPersistentContext()`, the same mechanism a normal Chrome profile is — preserves cookies, localStorage, IndexedDB, everything) — to rule out the storageState gap specifically. **Still rejected**, even reused locally within 15 seconds of the capturing browser closing.
5. **Headed (visible) vs. headless**, to rule out headless-browser detection (plausible given the reCAPTCHA cookie spotted in step 3) — tested by relaunching the same persistent profile with `headless: false`, identical to how it was captured. **Still rejected.**

Every failure shares exactly one thing in common: the browser that authenticated was closed, and a *different* browser process tried to reuse its cookies/profile afterward — regardless of storageState vs. full profile, headless vs. headed, CI vs. local, or how much time elapsed. The leading remaining theory is that Subsplash actively ends the session server-side when the tab/browser closes (some security-conscious apps do this deliberately, rather than relying on passive cookie expiry) — which would mean no close-and-reopen approach can ever work, no matter how faithfully the credential material is preserved. The only architecture that could plausibly get around that is a **single Chrome process that never closes** (started once, kept running indefinitely as a background daemon; a scheduled script would `connectOverCDP()` to it rather than launching fresh) — not attempted, given the escalating cost of each ruled-out theory and that it introduces a new class of operational burden (a long-lived process that must survive reboots and be manually restarted with a fresh sign-in if it ever dies).

Also confirmed and fixed along the way, independent of the auth problem, in case a future attempt gets further: a fresh `page.goto()` straight to a series' deep hash-route URL bounces through `/auth/logout?redirect=...` and never returns, 100% reproducibly, on every series tested — the dashboard is an Ember app (hash-routed), and a real user is always already sitting on a booted instance of it clicking through (a same-document hash change), never doing a fresh top-level load into a protected deep link. Setting `location.hash` via `page.evaluate()` instead of `page.goto()` fixes that specific problem — but it's moot without solving authentication first.

The automation code (`scripts/scheduled-sync-subsplash.ts`, `scripts/capture-subsplash-session.ts`, `scripts/lib/fetchSubsplashExport.ts`, the `.github/workflows/attendance-sync.yml` GitHub Actions workflow, and the `GET /api/attendance/series` route that existed only to support it) was removed rather than left around non-functional. `scripts/sync-subsplash-attendance.ts` (the manual half) is the permanent design.

## Alternatives rejected

- **Finish the native check-in app.** Solves a problem the church doesn't have — Subsplash Check-In is already the capture tool volunteers use at the door. Building a second one only to import from it later would be strictly more work for the same end state.
- **Subsplash webhooks.** No check-in event exists in the webhook event list; nothing to subscribe to.
- **Ask Subsplash for API access to check-in data.** Worth pursuing (see Consequences), but not something this app can wait on — it isn't available today.
- **Attendance *totals* export instead of per-person.** Subsplash's documented "export attendance totals" feature is aggregate-only. It would kill absentee tracking, series frequency by person, and email-parents — the reporting features this app exists to provide.
- **Full automation of the dashboard export.** Investigated in depth; see Consequences for the specific things tried and why each failed. Revisit only if Subsplash ships an API for check-in data, or if a long-lived-background-browser architecture becomes worth the operational cost.
